**Staging's PostgreSQL cutover and independent dump/restore were verified on 2026-08-31; production remains unchanged on SQLite.** The original staging SQLite database, image, keys and recovery snapshots were preserved. Five synthetic rows across 17 tables were imported and round-trip verified; later migrations, runtime grants, reconciliation, matching-key decryption and app restart passed. See [[Progress Log#2026-08-31 — Staging delivery activated and PostgreSQL cutover verified]] for recovery references and limits. A durable local PostgreSQL container with a generated local credential replaces the task's disposable scratch server. New synthetic walkthroughs can be created through the existing explicit demo login; prior SQLite walkthroughs remain in their original files until an authorized conversion.

The [PostgreSQL cutover runbook](../../ops/aws/ec2/postgres-cutover.md) identifies the source/destination checks, old-image/key/snapshot preservation, explicit import, reconciliation, recovery test, cutover point and post-write recovery limits. ## Database gaps addressed

| Gap | Implemented choice | Practical limit |
| --- | --- | --- |
| Divergent SQLite runtime and PostgreSQL proposals | One canonical PostgreSQL structure generated by Rails migrations; full fresh/upgrade/restore rehearsal | The larger RLS/clinical model in [[Data Modeling]] is still a proposal |
| Separate mutable office quantity and pharmacy movement history | One append-only `clinic_inventory_entries` ledger, with cached balances changed atomically by database triggers | Separate product catalogs remain; no clinical stock-use workflow |
| Same manufacturing lot received repeatedly | Shared lot/location position with independent immutable receipt headers/lines; supplier, invoice reference, quantity/conversion, optional cost/currency and actor/profile retained per delivery | No supplier connection, order/credit matching, valuation or fee calculation |
| Whole packages versus fractional units | Immutable product stock unit/precision and evidenced package conversion; exact PostgreSQL numeric quantities, no binary floating point or silent rounding | Countable units stay integral; mL/g support up to six decimal places. Package conversion is not a medication dose calculation |
| Unreliable writes and retries | Atomic balance updates, row/advisory locks, bounded quantities and clinic-wide retry keys with payload comparison | Large throughput/capacity remains untested; no automatic retry of uncertain arbitrary actions |
| One mutable batch status | Independent overlapping holds plus specific release records; stock availability excludes every unreleased hold | No sensor integration or automated recall feed; old status history remains retained |
| Counts overwrite stock or ignore intervening movements | Immutable count observation with ledger cutoff, separate approval and exact variance posting; stale counts are rejected | Pharmacy position counts are implemented, not formal controlled-drug counts or approval separation-of-duties policy |
| Coarse inventory permission | Separate catalog/receive/adjust/hold/release/count/configure permissions; active user/membership and current profile checked during writes, also in database posting guards | Existing inventory members retain prior access through explicit migration backfill. No permission-administration UI, MFA or trusted external capability issuer |
| No configuration provenance | Immutable clinic inventory profile versions, status, non-sensitive operator reference and actor/reason; UI can suspend posting without hiding history | Only synthetic inventory is supported. Per-location/operator capability matrices and clinical activations are not implemented |
| Weak historical integrity | Composite clinic/actor keys, append-only history, receipt-to-posting checks, metadata-only catalog audit and count linkage | Database owners remain privileged. Field-change metadata is not a full before/after audit or read-access audit |
| Unbounded dashboard aggregation | SQL balance/availability aggregation, indexed worklists, 25-product pages, 10-position pages and bounded recent histories | No full search/export/reporting system; query/load acceptance remains a later scale check |
| Owner credentials inside server / unsafe migration rollback | Prepared restricted runtime role, separate maintenance credentials, explicit migration job and PostgreSQL dump/restore procedure | Staging role/service installation is verified; production is pending. No RLS, independent audit sink, high availability, scheduled backup or monitoring claimed |

Balance and provenance restrictions also protect direct SQL paths against ordinary application mistakes. They are not proof of isolation against a compromised application identity: request actor IDs and local SQL context are not signed capabilities. All actual clinic reads still rely on scoped Rails authorization; the larger trusted-identity/RLS design requires a separately accepted security slice.

## Preservation and conversion

The synthetic legacy importer requires an offline read-only SQLite backup, exact known schema/version, explicit PostgreSQL connection and an empty target at migration 004. It validates integrity/foreign keys, imports in dependency order in one transaction, preserves primary keys, ciphertext and timestamps, checks every returned value, resets sequences and refuses a second import into populated tables. It never decodes or prints encrypted content. Subsequent migrations preserve legacy pharmacy entries as package units and freeze the old ledger tables as evidence.

Legacy office balances may contain initial quantities with no historical movement. Migration reconciles the difference with a clearly marked, unattributed legacy opening balance recorded at conversion, rather than inventing an earlier actor or time. Conflicting expiry dates for the same product/lot stop migration for review. Old batch holds are carried forward, without inventing historical review evidence or receipt costs.

Use `inventory:verify` for a read-only reconciliation of office/pharmacy cached balances against entries and receipt lines against postings. It prints discrepancy counts, not record contents. A PostgreSQL backup must be restored into a separate empty target with the corresponding application keys and runtime grants; a successful SQL dump alone is insufficient.
