# Staging owner review over HTTPS

Prepared 2026-08-31, extended and activated 2026-09-01 for two allowlisted
individual reviewers using wholly synthetic portal content. The protected staging
address is `https://44.218.229.179`. Public TCP 443 was opened only after the
founder accepted the exact current image findings for this bounded review.
Production is untouched.

## What is installed

- `apply-staging-review` owns Elastic IP `44.218.229.179`, its association with
  staging `i-011a8232817dc587f`, HTTP ACME ingress, two generated reviewer
  secrets, and exact-secret read access for staging's existing instance role. No other
  instance, volume, application key, or existing S3 resource is changed.
- TCP 80 serves only `/.well-known/acme-challenge/`; other paths return 404.
  There is no HTTP application or login. SSH, app/container ports and PostgreSQL
  remain closed to the internet. The original stack is not updated/replaced.
- Certbot 5.7.0 uses a separate Python 3.12 virtual environment. The real IP
  certificate is under `/etc/letsencrypt/live/apply-staging-review/`. Its first
  expiry is 2026-09-07 07:25:41 UTC. Certificate/private-key files stay on host.
- The authenticated edge is generated by `review_access.py`. All public HTTPS
  paths require Basic authentication; the Rails portal also requires ordinary
  login. Edge credentials are stripped before proxying. Exact Host and forwarded
  headers are fixed; browser Origin is preserved so CSRF rejects foreign writes.
  Rate limiting, no-store/noindex headers and existing app permissions remain.
- `/etc/apply/review-origin` configures only staging's canonical IP origin. Its
  presence on production causes the new launcher to fail closed. Default hosts
  without it retain `https://localhost:8443`. The private SSM endpoint still
  supports release health checks, but browser login uses the canonical IP URL.
- Renewal uses `apply-review-renew.timer`, twice daily with a randomized delay,
  and `apply-review-renew.service`. The reload hook validates nginx before
  reloading. This is certificate maintenance, not a general backup/monitoring
  schedule. No notification channel or response-time commitment is configured.

The IP certificate is free; normal AWS IPv4 and Secrets Manager charges apply.
Retained Elastic IP/secret resources can continue billing after stack deletion.
No domain, load balancer, new EC2 instance or subscription was purchased.

## Individual account handoff after activation

Retrieve the credential **in the operator's own private terminal**, never into
chat, a recording, a Run Command body, the vault or Git:

```sh
aws secretsmanager get-secret-value --region us-east-1 \
  --secret-id apply/staging/StagingDemoUser --query SecretString --output text
```

For the requested account, the values are username `StagingDemoUser`, app email
`staging-demo-user@example.test`, and a generated password. The same command can
use `apply/staging/owner-review` for the retained original reviewer. Each secret
supplies the edge username, app email and generated password. The
reviewer uses `username` in the browser's first authentication dialog, then
`email` and the same password at `/login`. Deliver it privately to the intended
individual; do not turn it into a shared team account. `prepare-reviewer.py`
creates only the selected allowlisted synthetic non-admin account and demo
paperwork, preserves the other managed gate identity, and refuses unknown or
colliding identities. For `StagingDemoUser` only, it also verifies the
release-seeded immutable clinic administrator role, creates the managed clinic
membership, and idempotently prepares the wholly synthetic clinic dataset. It
does not issue invitations or messages, and the ordinary owner reviewer receives
no clinic API access.
Do not casually rerun provisioning with a different secret: password rotation
and account/session revocation need coordinated operator handling.
