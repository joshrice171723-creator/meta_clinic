# PostgreSQL cutover and recovery

Source/runbook reviewed 2026-08-31. The working API, tests, SQL structure and release tools now use PostgreSQL 18.6, alongside an independently built static frontend. **The two installed EC2 bootstrap releases still use SQLite. No host cutover is claimed by the local checks.** The ordinary installer deliberately refuses to skip this procedure when legacy data exists.

Use only an authorized, wholly synthetic source. Stop if its classification is uncertain or if real information is found. Never download hosted databases, encryption keys or credentials into this repository. Preserve all four existing application secrets: database conversion does not rotate encryption keys.

## Chosen design

- One private PostgreSQL container per existing host, retaining independent environments and EBS storage. No RDS, public database port or new host is required. PostgreSQL 18 uses `/var/lib/postgresql` with a versioned data directory, backed by `/srv/apply/postgres` on encrypted EBS.
- `apply_runtime` is the Rails login: no DDL, TRUNCATE, owner/superuser privileges or history updates/deletes. `apply_owner` is a privileged maintenance identity in that environment's isolated PostgreSQL cluster; only the maintenance runner receives it. Do not treat this as a production clinical authorization model or RLS.
- Two additional generated managed secrets per environment, separate from encryption keys. At the [AWS Secrets Manager price rechecked 2026-08-30](https://aws.amazon.com/secrets-manager/pricing/) this adds about $0.80/environment/month before API calls; no new resource/cost is claimed as provisioned by these files.
- Start with 500 MiB Rails, 64 MiB static frontend and 256 MiB PostgreSQL limits on the accepted 1 GiB host; `max_connections=20`, `shared_buffers=64MB`. Container correctness checks use these limits. Capacity, long-running load, disk growth, backups and restore headroom still require review; PostgreSQL is not a claim that t3.micro is sufficient for clinics.
- Migrations precede server start with owner credentials. Runtime restart never performs DDL. Use a single application process until the process-local limiter and scaling design change.

## Preflight and installation

1. Finish the candidate checks in the [CI/CD guide](../../../APPlyVault/03%20Execution/CICD.md): Rails/frontend tests, formatting/build/security checks, `bin/verify-postgres`, root `bin/verify-web`, all offline release/launcher tests, individual host-shell syntax checks and both `verify-container.py --environment staging` and `--environment production`. The corrected launcher starts `apply-api` and `apply-web` under matching service names; offline tests exercise those branches without real host calls. Build independent `apps/api` and `apps/web` images, pass `--web-image` to the verifier, pin both verified digests and apply the existing image/security acceptance rules. A bootstrap exception is not permission to bypass the production promotion gate.
2. Verify both selected instance IDs against `targets.json`. Inventory non-sensitive counts/schema/version metadata only. Confirm source is synthetic and the four encryption-key references/versions are retained in protected recovery evidence. A 2026-08-30 read-only SSM preflight confirmed both four-migration legacy schemas: production has zero rows in the checked application tables; staging has one account, one inquiry and three guides, with no checked clinic records. Contents were not read. Recheck at the actual maintenance window rather than relying on that history.
3. Record old image, scripts/config, EBS volume and encryption-key version references. Take an encrypted EBS snapshot and await completion before changing the database. Agree the maintenance window and recovery decision point. Preserve the old SQLite file and image; do not delete or overwrite them.
4. Review an additions-only change set from `postgres-secrets.yaml` for each existing host role. This creates two secrets and one policy, with **no instance/volume replacement**. The changed main `stack.yaml` is for new PostgreSQL hosts; do not apply its changed UserData to an existing host blindly. Add only the resulting secret ARNs as `APPLY_DATABASE_OWNER_SECRET` and `APPLY_DATABASE_RUNTIME_SECRET` in its root-owned `/etc/apply/config`.
5. Install `postgres.sh` as `/usr/local/sbin/apply-postgres`, its systemd unit, the revised `apply-run.sh`, both `apply-api.service` and `apply-web.service`, the installer and trusted-edge `nginx.conf`. Preserve copies of old scripts for a pre-write rollback. `render-ssm-command.py` installs current files but its normal installer cannot perform a legacy conversion; stage files separately for this first cutover.
6. Stop `apply-web`, take an offline SQLite `.backup` under root-only `/srv/apply/backups`, and check `PRAGMA integrity_check`/foreign keys locally on the host. No WAL/SHM/journal sidecars may accompany the import source. Keep writes stopped until conversion and verification finish.
7. Start `apply-postgres.service`. Use the image's explicit `bin/rails db:migrate VERSION=20260830000400` maintenance job to create an **empty** `apply` database at exactly the four legacy migrations, with existing application encryption environment and new owner credentials. Do not run `db:prepare` here: it loads the latest structure instead of the required import target. Do not seed.
8. Run `bundle exec ruby bin/import-legacy-sqlite --synthetic /legacy/backup.sqlite3` in an isolated temporary maintenance container with a read-only mount of that backup and the same owner `PG*` environment. The temporary container needs Python 3 (the supplied application image includes it solely for this legacy tool). The importer validates schema, integrity, versions and emptiness; preserves IDs, ciphertext and timestamps; verifies every inserted value; and commits all rows together. Errors are suppressed, source is immutable, and retry into a populated destination is rejected. A failed later migration leaves this import intact for diagnosis, never an automatic reseed.
9. Run `/usr/local/sbin/apply-run prepare`, then `/usr/local/sbin/apply-postgres migrate API_IMAGE`. It applies the remaining migrations, seeds only the permitted environment's samples, creates the restricted runtime role and applies `db/runtime_privileges.sql`. Check `inventory:verify`, non-sensitive row counts, permissions and matching-key decryption of the known synthetic recovery marker without printing it.
10. Restore a PostgreSQL custom-format dump into a separate empty temporary database/volume, reapply runtime grants and check reconciliation/decryption using the same protected key versions. `pg_dump`/`pg_restore` are run from the PostgreSQL 18 container, avoiding client/server version mismatch. A same-volume backup alone is not disaster recovery.
11. Only after those checks, write the root-owned marker `/etc/apply/postgres-cutover-verified` and run the ordinary installer with the verified API digest, web digest and generation. Verify both application services/containers and the edge's `/up` (API) and `/health` (frontend) routes. Test private TLS, regular login/session behavior, encrypted synthetic inquiry persistence, restart, environment-specific demo policy, and clinic denial. Record actual results/both digests/backup references. Update the environment runbook only after success.

The fixed GitHub SSM release document is for ordinary releases, not this privileged cutover. Install/update its `image`, `webImage` and `generation` contract alongside the pair-aware host installer. It must not gain arbitrary shell, secret access or data-migration parameters. GitHub authentication/activation remains a separate open item.

## Recovery

Before PostgreSQL accepts any new user writes, a failed cutover can be recovered by restoring the preserved scripts/config/image and pointing the old application at its unchanged SQLite database. Stop PostgreSQL candidate writes first; never operate both as writable sources. Do not remove failed conversion evidence or rotate keys.

After new PostgreSQL writes, reverting to SQLite would lose work. Use a deliberate PostgreSQL backup/restore or forward fix with reconciliation and an explicit recovery decision. Never down-migrate the immutable inventory history or restore over a populated database. Preserve source/destination snapshots and matching key/image references until retention/disposal is approved.

Regular release backups use `apply-postgres backup /srv/apply/backups/NAME.dump`; off-volume snapshots, retention, scheduled monitoring/backups, RPO/RTO and a responsible operator are still required. Nothing here creates recurring jobs or certifies HIPAA/clinical readiness.
