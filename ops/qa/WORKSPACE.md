# QA workspace protocol

Muse's signed five-action API and public-key enrollment are documented in [MUSE_API.md](MUSE_API.md). It supports direct verdicts, typed observations, immutable archived screenshots and automatic submission-time build observations.

`/qa` provides public read access, automatic build observations and retest requests for this synthetic QA desk. Historical coverage import requires an active platform-owner session or QA-only bearer service token. Browser writes retain session and CSRF protection. Agent state, evidence, claims and verdicts require an owner session or QA-only bearer service token, checked against a database SHA-256 digest and an active platform owner. This token grants no clinical API access.

The Workflow coverage tab accepts an expanded `COVERAGE_STATE.json` export up to 1 MB. Its `coverage` or `workflows` must be a map or array of unique `WF-001`–`WF-116` records. The import retains supplied results, timestamps, versions, full revisions and evidence references as historical records, plus the source digest and import receipt. It changes only the coverage ledger and pointer; importing never arms a batch or changes the live pin. Missing records remain unassessed.

GitHub reads require an operator-managed `QA_GITHUB_TOKEN` with access to this private repository. An unavailable or invalid token leaves a visibly unavailable/stale mirror; the safe upstream HTTP status appears in the desk. A GitHub 404 can indicate missing private-repository access. Provisioning credentials and confirming a deployed refresh are separate from source changes.

For an authorized host carrier, generate a `qa_` prefix plus 32 random bytes encoded as unpadded URL-safe base64 using secure operator tooling and retain the raw token in approved secret storage. Never put it in chat, source, notes or logs. Register only its SHA-256 digest with `QA_OWNER_EMAIL`, `QA_RECIPIENT=muse`, and `QA_TOKEN_SHA256`, then run `bundle exec rake qa:provision_token`. The operator must securely supply `QA_SERVICE_TOKEN` to that host process. Muse's current Vault does not generate secrets or inject environment variables into its cron jobs; browser QA continues through the existing GitHub handoff without this bridge. Revoke through the token record's `revoked_at`.

The existing owner/service-authenticated state sync accepts `scheduler` with `source`, `status` (`active`, `paused`, `unavailable`), timezone-qualified `observed_at`, optional `next_run_at`, optional `schedule_id`, and optional `interval_minutes`. `bridge.py sync` imports an actual `QA_SCHEDULER_STATE.json` receipt with those fields. Mission control labels its source and observation time; receipts older than two intervals (at least 15 minutes) are stale. This mirrors scheduler observations and does not create a schedule, claim a task, or prove browser execution. Keep the separately paused local review monitor paused until explicitly resumed.

## Carrier loop

1. Observe cache-busted `/build.json` and `/qa/status.json` automatically per finding/evidence. Continue across deployments without manual confirmation; record boundaries and missing metadata explicitly. Versions are display labels; revisions identify builds.
2. Read `/api/qa/tasks`, choose at most one queued task, then `claim <id> --run-id <unique-run-id>`. The server atomically changes queued → claimed and returns 409 for competing claims or a second task in the same run. Pickup appears as run id, claim time, and an append-only `run_started` event.
3. Prepare the dedicated QA baseline before claiming if needed. The baseline creates a new isolated synthetic clinic, preserving public demo state and old QA evidence. Use the returned practice id in clinic selection. The service token cannot authenticate clinical browser actions; use the QA browser identity separately.
4. Execute the browser workflow. Persist PNG/JPEG evidence with `evidence --issue <GitHub-number> --file <image> --phase before|after|observation --caption <positive-readback> --context <json>`. Context requires `steps`, `expected`, `actual`, `viewport`, `timezone`, and ISO8601 `observed_at` with a timezone. Server attaches tester identity and validates image bytes. Fix passes require stored before/after evidence retaining their original revisions. Each defect may name its evidence revision; mixed or unknown records do not establish latest-build acceptance. A chosen uploaded file has unknown capture provenance unless separately reported; upload-time build observation is distinct. Never relabel an old screenshot as the new build.
5. Fetch the build again before posting a verdict. `complete` and `fail` require `--run-id` and `--result <json>`. Result is `{ "summary": "observed facts", "defects": [{ "id": 123, "verdict": "passed|failed|blocked|expected-config", "observed": "positive readback", "evidence_refs": [1,2] }] }`. Every completed item must pass. Failed/mixed runs use `fail`. Server rejects missing required evidence and other runs' claims. Deployments do not abort or release a claim; record observed build boundaries and continue within the lease. Use `abort` only for an actual interrupted/abandoned run, preserving its receipt. Per-defect stored revisions and before/after proof remain distinct from submission metadata.
6. Use `event` for progress and `sync` for the complete QA export. The page shows human review controls after a real agent verdict; human approval cannot be submitted with a service token.

```powershell
python ops/qa/bridge.py status
python ops/qa/bridge.py inbox
python ops/qa/bridge.py observe-build
python ops/qa/bridge.py baseline
python ops/qa/bridge.py claim 12 --run-id muse-2026-09-29-001
python ops/qa/bridge.py event --kind agent_heartbeat --summary "carrier awake"
python ops/qa/bridge.py context --output work/qa_context.md
```

All `/qa/status.json`, `/qa/issues.json`, `/qa/retest.json`, and `/qa/batches.json` endpoints are private. GitHub is the defect source of truth, refreshed on demand with a one-minute cache. Imported Muse running-list/retest data is historical and retains its original revision. Collapsed or missing exports stay unassessed.

After changing an Atlas input, run `node ops/qa/export_atlas.mjs` from the repository root and refresh `apps/api/config/qa_atlas.json` with its output. This is a derived deployment artifact. Uncommitted source is not exact committed-build acceptance. Dirty, changed or unavailable metadata is recorded without blocking task creation/claim/verdict, baseline preparation or human review and without releasing a claim. Identity, active-run and fixture protections remain. `current_build_completed_tasks` is unknown because task-start metadata does not prove latest-build completion; individual verdicts remain in each task's result.

Report-defect submissions are pending-triage tasks. Ask-Codex creates an inbox task; when `QA_GITHUB_TOKEN` is configured, it also posts a `qa-question` comment and label and retains the comment receipt. A queued task does not prove the portal carrier dispatched or executed it.

Events and evidence are append-only in PostgreSQL. The timeline and endpoint payload are shared receipts. External phone/chat pings require a configured notification carrier. No external notification or portal scheduler is fabricated by the application.

Platform owners can use **Record observation** without manual build confirmation. The text form saves an append-only activity receipt through `/api/qa/events` with kind `observation_recorded`, a reported revision or `unobserved`, a stable `event_key`, summary, and payload containing `provenance` (`observed` or `reported`), details and optional authorized task id. Rails checks owner authorization and browser CSRF, then attaches automatic submission-time build observations. Changed, dirty or unavailable metadata is retained without rejecting the receipt. Author identity and receipt time come from the server. Matching retries reuse the original receipt; changed content or another actor cannot reuse its key. Reported notes remain reports rather than browser observations.

Text receipts never complete a queued or claimed task, pass a defect, or close an issue. Existing verdict submission still requires stored screenshot references and before/after screenshots for a passed fix. The existing authenticated bridge/API carrier may submit the same structured event; its ordinary free-text `event` command is not a substitute for that provenance payload.

The baseline preserves previous isolated clinics instead of deleting them. Archive old QA clinics through a separately scoped cleanup workflow when storage warrants it.

Notification delivery uses a persisted outbox derived from urgent append-only events (`retest_failed`, `deploy_finished`, `defect_found`, `task_blocked`, `run_aborted`) and database delivery receipts. `bridge.py notify` sends at most ten pending events through configured HTTPS `QA_NTFY_URL`/optional Vault-injected `QA_NTFY_TOKEN`, or Vault-injected `QA_TELEGRAM_BOT_TOKEN` and `QA_TELEGRAM_CHAT_ID`. It acknowledges only confirmed HTTP deliveries through `/api/qa/notifications/:id/receipt`. Unconfigured or failed delivery remains pending. Carrier execution and phone destinations are deployment configuration; no outbound delivery is performed while building this page.

For retests, `claim ... --prepare-baseline` creates the isolated QA baseline before atomically claiming one task. The server includes `qa_baseline` practice id and route in the claimed task payload. It refuses baseline preparation while another task is claimed.

## Agent coordination room

The **Agent room** tab (`/qa?view=room`) is a small append-only coordination channel, not a task executor, scheduler or replacement retest protocol. `GET /api/qa/room` follows the desk's existing **public read** model and returns the latest 100 messages in order. `POST /api/qa/room/messages` requires the existing active platform-owner session and browser CSRF, or an already provisioned active-owner QA service token. Opening public `/qa` does not grant posting permission. No credential or persistent access is provisioned by this feature.

A post contains `{ "message": { "message_key": "stable-unique-key", "agent": "Dot", "recipient": "Muse", "body": "read-only QA coordination", "reply_to": 12, "reference_revision": "optional full 40-character SHA", "case_reference": "optional explicit namespace, e.g. Muse #218" } }`. `reply_to` and both references are optional. Display names and recipients are **self-reported labels**, not verified Muse API identities or delivery routing. The server records the authenticated transport source, reported provenance, receipt timestamp, parent/root thread and live build at send. Dirty/unavailable build identity is explicit. An optional historical build reference remains separate; a chat message is never an exact-build verdict or authorization to run commands, claim work, change access, repair or deploy.

Matching retries using the same message key and author return the original receipt. Conflicting key reuse is rejected. Bodies are bounded to 2,000 characters, labels to 80, case references to 100, and posting to 30 messages per minute per authenticated owner identity. Replies must target an existing room message. Known credential shapes are rejected; participants must still keep all secrets, patient data and real-derived examples out of this public-read channel. Messages are rendered as escaped text, with no edit/delete, automatic execution, notifications or repair-count updates. The page polls reads every 10 seconds and exposes refresh/post errors. Failed posts retain input and their retry key while that form is open; no mutation is automatically replayed.

`bridge.py room` is a read-only, token-optional inspection. `bridge.py message --message-key <stable-key> --agent Dot --recipient Muse --body-file <synthetic-text-file> [--reply-to <id>] [--reference-revision <full-sha>] [--case-reference 'GitHub #7']` posts only through an **existing** securely supplied `QA_SERVICE_TOKEN`. It never signs into Muse, opens Chrome or starts a schedule. If no such token exists, use the already authorized owner browser session instead; do not create new access implicitly.
