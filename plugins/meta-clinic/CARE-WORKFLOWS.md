# Connected clinic-day workspace

The `CareJourney` panel presents the existing Rails patient and visit workflow. It reads authorized records with `meta_clinic_read` and sends every proposed mutation to the coordinator's existing `onPrepare(operation, arguments)` review dialog. Opening a review is not a save. Rails owns permissions, persistence, linked-record validation, versions, evidence and operation receipts.

## Integration

`CARE_OPERATIONS` is merged into the existing catalog with eight new operations. Existing encounter, patient lookup, appointment, observation, vital dictionary, note list, billing service and invoice operations retain their IDs and contracts.

Render `CareJourney` with `{ call, onPrepare, refreshKey, context }`. `call` returns structured tool content and throws on failures. `refreshKey` refreshes selected encounter resources after a confirmed save. The component clears its records and selections when the account, practice, selected site or authorization generation changes. Unsubmitted note and follow-up inputs survive an ordinary encounter refresh; newer backend versions block another review until the user explicitly reloads. Selecting another patient/encounter or discarding edits requires confirmation. The parent should also preserve its existing navigation and pending-review controls when leaving this domain.

## Implemented pathway and source contracts

| Stage | Operations and record source | Guards and outcome |
| --- | --- | --- |
| Find patient | Existing `lookup_patient`; backend name/reference search, 20 matches | Only returned patient IDs are selectable. No invented identities or cross-clinic search. |
| Select appointment or encounter | Existing `list_appointments`, `get_appointment`; existing `list_encounters`, `get_encounter` | Patient-specific reads; up to 50 appointment and encounter rows. Server validates patient ownership on encounter detail. |
| Start scheduled visit | Existing `start_encounter`: `POST /api/clinic/patients/:patient_id/encounters`, body root `encounter` | Re-read appointment before review and compare patient, encounter binding, status and update timestamp. Rails locks the appointment, authorizes `encounters.write`, and returns the existing encounter or creates one. There is no fabricated arrival status. |
| Record vital signs | Existing `vital_sign_dictionary` and `patient_observations`; new `record_vital_signs`, body root `vital_signs` | Fields/units, dictionary version and `can_write` come from Rails. User enters exact decimal strings and observed time, explicitly confirms patient identity, then reviews the request. Re-read dictionary before preparing. Rails rechecks dictionary, units, paired blood pressure, open encounter and `observations.write`; backend computes any supported derived value. |
| SOAP draft | Existing `encounter_notes`; new `note_templates`, `get_encounter_note`, `create_soap_draft`, `revise_soap_draft` | Template IDs/versions/cautions and existing note sections come from Rails. Template text is applied only on user request. Re-read current SOAP metadata before review; revisions retain `expected_revision`. A signed current revision is read only in this panel. Patient instructions remain draft text. |
| Follow-up | New `encounter_follow_up`, `record_encounter_follow_up`, body root `follow_up` | Status enum comes from the existing service contract. Eligible appointments and assignees come from its response. Preserve current due time unless the user changes the decision; require plan for needed/arranged and a returned appointment for arranged. Re-read the record ID/version; submit `expected_version`. |
| Complete encounter | Existing `encounter_completion`; new `complete_encounter`, body root `close` | Decisions use backend-returned options. Show actual follow-up, signed-instruction, education and open-task evidence. Require explicit unfinished-work acknowledgment; reset it when evidence changes. Re-read evidence before review and send its exact follow-up version/state, education IDs and task version strings. Rails locks and rechecks evidence and blocks active video sessions. |
| Start checkout | Existing `patient_invoices`, `billing_services`, `draft_invoice` | Encounter must be completed. Choose an active returned catalog service; price/currency/lock version remain backend-owned and quantity stays an exact decimal string. Re-read encounter, service and invoices before review. Prepare one unposted invoice line; an existing returned non-void invoice prevents duplicate preparation in this panel. |

Executable references are `apps/api/config/routes.rb`; controllers `clinic/scheduling/{appointments,encounters}_controller.rb`, `clinic/care/{vital_signs,note_templates,encounter_notes}_controller.rb`, `clinic/operations/encounter_follow_ups_controller.rb`, `clinic/billing/invoices_controller.rb`; services `clinic/scheduling/{create_encounter,encounter_completion,close_encounter}.rb`, `clinic/care/{vital_signs,create_encounter_note,revise_encounter_note}.rb`, `clinic/operations/encounter_follow_ups.rb`; and serializers `clinic/scheduling/{appointment,encounter}_serializer.rb`, `clinic/care/encounter_note_serializer.rb`, `clinic/billing/invoice_serializer.rb`, `clinic/billing_service_serializer.rb`.

Each resource read has its own error state. During a refresh, a failed resource retains its last confirmed records and form inputs with its controls disabled until a successful read; independent available workflow sections remain open. An unchanged vital-sign payload keeps the same local request key across review attempts so an explicit second review does not create a new idempotency identity. UI capabilities control visibility or disabled states; Rails reauthorizes the actual encounter site and action on every protected request. No failed mutation is automatically replayed by this component.

## U.S. standards basis

Reviewed on 2026-10-04 following `docs/development/healthcare-standards.md` and its U.S. reference map. The [FHIR Implementation Guide Registry](https://fhir.org/guides/registry/) was opened as the discovery entry point; its guide table requires browser JavaScript, so applicable published HL7 pages were opened directly. The originally selected STU8 links redirected through the publisher's technical correction pages to **US Core 8.0.1, STU 8, trial use, based on FHIR R4**. The pages identify 9.0.0 as a newer version; this bounded review pins 8.0.1 consistently and does not select a production exchange version or claim conformance.

| Reviewed reference and section | Applicability and implementation interpretation |
| --- | --- |
| [US Core 8.0.1 Vital Signs Profile](https://hl7.org/fhir/us/core/STU8.0.1/StructureDefinition-us-core-vital-signs.html), Mandatory and Must Support Data Elements; Profile Specific Implementation Guidance | U.S. quantitative observation exchange distinguishes patient, clinical time, value, unit, components and absent reasons. This panel retains backend patient/encounter linkage, entered observation time, exact values and returned units; it displays absent values separately and never invents clinical ranges. It changes no observation model, coding or conversion. Exchange cardinality does not make every field a required UI measurement. |
| [US Core 8.0.1 Clinical Notes](https://hl7.org/fhir/us/core/STU8.0.1/clinical-notes.html), Clinical Notes; FHIR Resources to Exchange Clinical Notes | U.S. note exchange guidance focuses on existing notes and exchange representation; it does not prescribe SOAP content requirements. This panel reuses the backend's existing SOAP sections, template/version metadata and draft revisions. It creates no FHIR exchange, new note type or automatic signature. |

No clinical treatment, protocol, diagnosis, default normal finding, mandatory follow-up interval or completion decision is inferred from these guides. Workflow status enums and permission gates are existing Meta Clinic backend contracts, not new U.S. legal or clinical requirements. A field-by-field FHIR export mapping and conformance validation remain outside this slice.

## Deliberate coverage limits

- This panel starts an **existing scheduled or confirmed appointment**. Booking/rescheduling remain in the Schedule panel. Walk-in creation, a separate arrival timestamp, room/provider assignment, intake question tasks and nurse handoff ownership are not added here.
- Vitals entry covers the backend dictionary's numeric fields. Missing/declined readings, longitudinal correction, interpretation and clinical reference ranges are not synthesized. The display is one observation page, not a complete chart.
- SOAP signing, corrections of signed content, psychotherapy notes, Scribe capture/review, orders, medication administration, labs, documents and patient education recording remain in their owning workflows. Completion uses existing signed instruction/education evidence and never manufactures it. A user must not choose “not required” simply to bypass absent evidence.
- Follow-up recording uses existing disposition and optional returned ownership/appointment choices. Follow-up completion/reopening, scheduling a new follow-up appointment and task lifecycle management remain in their owning workflows. Completing the encounter does not complete outstanding work.
- Checkout prepares one catalog-backed draft invoice line. Invoice editing/posting, payment collection, insurance submission, online payment, external messages and claims are not performed by this panel. Invoice lists and catalog reads are bounded pages; absence on a page is not proof of exhaustive history.
- The scheduled encounter-start endpoint has no request key or client-supplied version field. The panel re-reads before preparation; Rails' lock and existing-encounter lookup supply its duplicate guard, but there is no new atomic comparison of the earlier appointment timestamp at apply time.
- These source changes do not add authentication or clinical release authority, schema migrations, FHIR export or hosted deployment.
