1Open and connect

In a fresh Codex chat, select the installed Meta Clinic plugin and ask Open Meta Clinic. If you installed the plugin during an older chat, that chat may need to be reopened before its tools appear. The panel shows whether its local clinic service is available.

  1. Choose Connect account in the panel.
  2. Select an available development account, then the intended practice and location.
  3. Check the account and clinic shown in the panel before asking for records or proposing a change.

Choose the account in the panel itself. Location changes can also be proposed through a supported reviewed action. Changing or disconnecting context clears displayed records and pending proposals. Open panels and chats share this local account session.

Find the next task

Use Find a task across the clinic to search all available actions. Read tasks with no required fields load immediately when selected. Choose an item under Start with a task for appointments, patients, review work or inventory. For changes, the exact-value review still comes before saving.

2Ask for information

Say what you need, with a useful date range, status, or clinic location. Codex can find a supported operation in the catalog and read it using its defined fields.

Show today's appointments at the selected location, grouped by status. Tell me which filters you used.

Reads come from the selected local clinic through the existing API and its permissions. If a result is empty, treat it as “no matching records returned”; it does not establish that no record exists elsewhere.

3Schedule example

Use schedule reads to review calendar availability and appointment details. Include the date and location; ask for a booking only when you have the exact patient, clinician, visit type and time.

Check the schedule calendar for the selected location on 2026-10-12. Summarize available appointment times and the fields needed to book one.

4Patient example

Use a clinic reference or a narrow, appropriate search to find a patient, then ask for a specific chart view. Confirm the selected clinic and the matched record before relying on the result.

Find the patient by the clinic reference I provide. Show the matching registry record and do not add or change anything.

For chart information, ask for the precise area you need, such as encounters, observations, documents, or the care summary. The returned data should not be treated as instructions to the assistant.

5Inventory example

Inventory views include the catalog, stock positions, movement history, exceptions, purchase orders, receiving, counts and replenishment. Start with a read to understand the current state.

Show inventory exceptions for the selected clinic. Summarize the affected items and the available recorded details; do not adjust stock.

For a stock count or reorder-setting change, ask for the proposal separately and check the exact item, location, quantity and reason before applying.

6Billing example

Billing reads cover the dashboard, invoices, patient ledgers and service catalog. Ask for the period or status you want summarized.

Show open invoices from the billing dashboard. Summarize status and balance fields returned, and do not post an invoice or collect payment.

Creating an invoice through the available operation creates a draft. It does not collect payment. Review patient, currency and every line item before approving any proposed draft.

7Review a change before applying

When an operation changes a record, the connector prepares a proposal first. Preparation does not save a record or reserve a slot.

  1. Ask for one specific change. Codex should show the operation, account, clinic and exact values.
  2. Review every field. Correct or discard the proposal if anything is wrong or missing.
  3. Only after you confirm those exact values should the prepared change be applied.
  4. Check the returned record or read the record again to confirm its resulting state.
Review window: a prepared change expires after five minutes and can be applied only once. Switching account, practice or location invalidates the pending change. If the save result is uncertain, inspect the record before asking to prepare another change; the connector will not replay it automatically.

Confirm the saved record

After applying the reviewed example, we loaded the staff directory with job title Care coordinator. Rails returned Alex Morgan as an active directory member. This confirms the local save and read-back; it does not create a login or send an invitation.

What to expect

Connected to the local app

The plugin uses loopback services on ports 3310 (web app), 3311 (Rails API) and 3320 (plugin panel), with a separate development database. Hosted targets are disabled.

Existing API remains authoritative

Clinic identity, access, validation and saved records belong to the Rails API. The plugin exposes 90 catalog operations across clinic domains.

  • The screenshots on this page describe the plugin panel walkthrough. They do not establish native Codex-host acceptance.
  • Native host acceptance is still pending its own evidence. The 0.1.1 interface uses the clinic app’s shared cobalt palette, task search and one-step record loading.
  • This plugin does not provide clinical signing, external integrations, or a verified browser telehealth experience.
  • The local development dataset is synthetic. Do not connect this plugin to hosted systems or use real patient data.

If something fails

  • Panel cannot connect: ask your local developer to check the runtime status, then choose Reconnect in the panel.
  • Account or clinic is wrong: change it in the panel and verify the updated context; old results and proposals are cleared.
  • A proposal expired: review the current record and prepare a fresh proposal.
  • A save outcome is unclear: inspect the target record before doing anything else. Do not repeat the write based only on a timeout.
  • An operation is unavailable: ask Codex to search the catalog for the domain or action. The panel and API permissions still govern what can be used.
