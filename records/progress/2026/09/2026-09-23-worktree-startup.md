# Prepared worktree startup proof — 2026-09-23

This is local synthetic development evidence for the Windows checkout. It does not establish browser journey, deployment, clinical, or release acceptance.

An isolated patient-journey checkout needed 5m30s to prewarm locked dependencies (165 pnpm packages reused, zero downloaded), 4m51s for setup (about 4m37s in the first database migration), and a failed cold start at the former 45-second API readiness limit. A retry with 180-second limits reached HTTP readiness in 78 seconds and finished startup in 2m14s. The first managed stop later failed because Ruby's Windows `Process.kill(0, pid)` reported an exited API process as alive while its handle remained open. A native exit-code probe detected that process correctly; the same checkout then stopped in 9.11 seconds, preserving its database volume.

The [shared resource helper](../../../../bin/agent-resources) now supports a third protected prepared slot. Newly prepared slots reserve a separate PostgreSQL container and host port; the first two already-claimed slots retain their saved environments until explicitly re-prepared. The [development lifecycle](../../../../bin/lib/development_lifecycle.rb) now allows 120 seconds for cold API readiness by default and checks Windows process exit state before declaring a managed PID alive. The [browser smoke script](../../../../apps/web/scripts/browser-smoke.mjs) can use a development account with multiple authorized locations and select a required clinic location. These changes reached `main` in merges `b19108cd` and `d90c8037`.

Slot 3 was created and dependency-prewarmed at `d90c8037`. Its first prewarm took 8m13s, including 7m46s in pnpm hard-linking from the local cache with no downloads; re-prewarming the same clean slot took 3.86 seconds. A first database setup against the existing default PostgreSQL volume was refused because that volume lacked its local credential file; it was neither reset nor regenerated. After slot 3 received its dedicated `apply-postgres-prepared-3` container and `54403` host port, fresh database setup succeeded in 3m08s, including 2m51s for migrations. A subsequent prepared-slot `bin/dev start --no-browser` reached API and web readiness in **42.24 seconds** with the schema already current. `bin/dev stop` passed in 12.90 seconds. The clean slot was released with its locked dependencies and persistent development database ready; services and container were stopped.

A separate 27-second SQL schema-load trial was not adopted: the checked-in snapshot produced 195 migration rows, 257 public tables, and 1,075 public indexes, while a fresh run of the 192 source migrations produced 192 rows, 253 tables, and 1,060 indexes. The four extra snapshot tables were `clinic_learning_export_batches`, `clinic_learning_inquiries`, `clinic_learning_moments`, and `clinic_learning_sources`. That difference needs a schema-ownership review before replacing migration-based fresh setup. Timings vary with host load and the shared heavy-command queue; they are measured runs, not a guaranteed startup target.
