## Source contract

The operator explicitly saves the already previewed four-field plan before any destination application. The new encrypted `Clinic::OfferingTextBatch` document stores the supplied source clinic/digest/time, each selected source and destination offering ID, original before/after changes, original destination revision, exact PATCH path/body/request key, independent item states, and append-only operation events. Server-derived actor ID, membership, practice, selected site (including explicit all-sites context), and authorization generation are immutable batch metadata. Submitted statuses or actor/tenant identities never confer authority.

The controller and owner reuse the existing `facilities.write` / established `appointments.write` bridge. Every list/read/save/prepare/reconcile/apply reauthorizes the active actor and practice. Batches are scoped to the original membership, actor, site and authorization generation; a changed permission generation cannot silently reactivate an old plan even after regrant. The controller compares the captured context with the request's current server session before writes. Composite practice/membership and practice/site foreign keys enforce tenancy. No grants or role changes are introduced. Original selected text remains configuration content; no patient records or clinical defaults are read or written.

Serialized saved reviews are capped at 1 MB and 500 explicitly selected items; larger selections must be split into separately reviewed plans. The server validates the saved plan against current existing DRAFT offerings and exact revisions, field allowlist/length/nonempty restrictions, actual before values, selected after values, existing/batch code collisions, unique source/destination mapping and distinct original request keys. Supported fields remain `name`, `code`, `contact_instructions` and `referral_instructions`. Only those attributes reach `ManageServiceOffering.update`; original operation, optimistic revision, receipt, audit and normalization semantics remain authoritative. No catalog identity or operational/profile field is mapped. No destination creation, consolidation or transition is implemented.

## Durable apply and receipt recovery

1. **Save reviewed text-import batch** persists the immutable reviewed requests, using a separate stable batch identity. A repeated save with that identity must match the original plan. A missing save acknowledgment cannot enable application; the exact batch can be looked up before proceeding.
2. **Apply reviewed draft text** first commits a per-item unknown intent via `prepare`. Only after that acknowledgment does the browser request application. Interruption before/after dispatch therefore leaves a saved unresolved item, with the original request intact. Preparation and application are separate acknowledged operations; no browser auto-retry is added.
3. Application is server-owned orchestration of the same offering update, not a new general mutation operation. The batch row, membership generation, exact receipt key and offering revision are locked using existing transaction/authorization patterns. Successful offering writes, existing idempotency receipts and the applied item outcome commit together. Destination update rejection rolls back its savepoint; the already durable intent and exact identity remain unknown rather than being cleared by a denied retry.
4. **Reconcile original receipt** reads the original actor/practice-scoped operation receipt through a small `Idempotency.reconcile` helper. It takes the existing exact-request lock and verifies the operation and canonical payload with the receipt's original digest algorithm/key. A matching committed receipt confirms that item without another destination write. An unconfirmed receipt or conflicting identity cannot enable repeat. No receipt found leaves the item unknown; it permits only another deliberate exact repeat through the existing owner. Receipt absence is not described as proof that an old HTTP delivery never happened.
5. Reload lists the latest 25 authorized same-context reviews, with a cap disclosure and exact-key lookup for older reviews. Restoring makes no destination mutation and disables unknown-item retry flags until explicit current receipt reconciliation. Displayed per-item requests remain unchanged; successful items are excluded from continuation. Any unknown item blocks unattempted item application. Completion requires every item to be confirmed applied.
6. Permission/session/clinic loss stops new browser destination requests. Every server action also rechecks the original context and authorization. Unmount stops continuation. A saved unknown review may be closed because its exact requests and outcomes remain on the server; it is not represented as resolved or undone.

## Precise retention and recovery limits

The inspected [hardening contract](../../docs/development/non-vendor-clinic-hardening-plan.md), section 9, leaves the actual retention period, owner, legal-policy version and hold behavior unselected and prohibits a destructive retention job before acceptance. The [domain boundary](../../APPlyVault/03%20Execution/Clinic%20Domain%20and%20Data%20Boundaries.md) likewise retains that human gate. Existing operation receipts are immutable and have no imported-batch retention policy to inherit.

This representation explicitly records `retention_policy: unselected`; it adds no TTL, purge, deletion endpoint, default period or destructive cleanup. Retaining synthetic development evidence while its policy is unselected is an engineering limitation, not an accepted indefinite-retention policy. Any real/production use, retention/deletion automation, legal hold handling, actor/site transfer, reauthorization across a changed generation, or replacement-owner continuation requires a separately accepted policy/contract. None is silently implemented.

The sequence remains non-atomic across items. There is no rollback/compensation, no source-authenticity verification, no catalog migration, and no automatic replay. Saved plans store selected text and before/after evidence, not the full source snapshot. A stale or rejected exact request is not rebased or assigned a new key: it remains in its original review, and a new explicitly reviewed plan is separate work. Unresolved original items continue to prevent that review's all-applied claim. The ordinary original per-update receipts remain the evidence of committed destination changes.
