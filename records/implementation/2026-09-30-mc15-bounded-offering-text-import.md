## Apply contract and technical choices

1. Keep the existing destination ID and all unselected fields. Reject same-clinic source selection, invalid/duplicate source records, unsupported/duplicate field selections, absent/empty/oversized source text and known destination code collisions. Null/absent source values never clear destination text. Reject a no-op selection.
2. Display every actual selected replacement as field / current destination value / normalized source value. Trimming and length limits match the existing text-edit operation. Selection, file loading and preview make no mutation request. Import stays disabled while ordinary edits or an unresolved save are pending.
3. Require a deliberate **Apply selected text to this draft** action. Submit only changed text plus `lock_version` and a fresh `request_key` to the existing `PATCH /api/clinic/service_offerings/:id`. Existing server-side current-membership, practice ownership, `facilities.write` / established legacy `appointments.write`, stale revision, retired-record and uniqueness checks remain authoritative. The browser convenience is narrower than the existing normal update endpoint; it grants no new authority. A draft published after the preview changes its revision and is rejected by that precondition.
4. Reuse `ManageServiceOffering.update` and `Clinic::Idempotency`: the update transaction and durable actor/practice-scoped receipt commit together; the same operation/key/canonical payload replays without reapplying writes, and changed-key reuse conflicts. Actor authorization is checked again on replay. The existing UI retains the exact attempted request in memory after an unknown outcome, blocks other changes and offers explicit exact retry. There is no automatic replay, browser-storage persistence, new receipt mechanism or claim of request restoration after page reload.
5. Normal offering history/audit is retained by the owning operation. This slice does not create a migration batch record or persist supplied source-file provenance server-side. The displayed source digest is supplied provenance, not authenticated source-system identity. The file is read locally; only selected text is submitted by the ordinary configuration action.

These are bounded reuse, input validation and presentation choices under already supported writes. No new healthcare data field, clinical rule, terminology mapping or exchange contract is introduced; prior source-reviewed service-directory fields remain unchanged.
