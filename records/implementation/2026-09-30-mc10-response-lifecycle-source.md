# MC-10 response evidence and local cancellation/fill lifecycle source batch

Date: 2026-09-30. Base: `f0269c37c61798bf3f3d8c896ee769592264d6fe`. Branch: `codex/mc10-response-lifecycle`. Authorized scope: one source batch and branch publication, without tests/build/lint, PR, main integration, deployment, access provisioning or percentage claims.

## Requirements mapped to source

The accepted [original prescription plan](../../docs/development/prescription-transmission-plan.md), MC-10 and the [RX-01–03 / OP-07–08 / OP-12 contracts](../../docs/development/meta-clinic-build-and-acceptance.md) require version-bound preparation, response identity/code/text/time, reconciliation against original identifiers, preserved cancellation/replacement chains and a simulated RxFill notice distinct from dispensing. The preceding preparation/provenance and exact legacy receipt replay work is retained.

`PrescriptionLifecycleRequest` is immutable local cancellation or fill-notice-simulation intent: original attempt/revision, actor/time, stable request key, original correlation and a separate local request correlation. Saving it creates no send or received evidence. Pending/result state is derived from immutable response journal rows; saved work never runs automatically.

`PrescriptionResponseEvent` is an immutable, audited journal. Every row retains original patient/practice/revision/attempt/correlation, actor and local recording time, simulator source/identity, local schema version, canonical digest and stable request identity. **Received** simulation rows also have a simulator message identity, local response code/text and received timestamp. **Unknown/unavailable** local outcome rows deliberately have NULL received timestamp/message/code/text; they cannot imply any response was received. No externally sent time is invented.

`PrescriptionSimulation` is a backend-only bounded local response generator. Its codes/text are explicitly local simulation values, not guessed vendor schemas or NCPDP codes. New submission executions append received evidence only for bounded known-response scenarios; failure-before-send, unavailable/revoked and unknown outcomes do not fabricate receipts. Exact submission replay returns prior evidence without creating inbound history.

`PrescriptionResponseWorkflow` exposes explicit authorized request/result operations. They recheck the selected patient/site and original attempt site, active actor and original correlation; use existing actor/practice/key/digest receipt semantics and the same prescription-series transaction lock; and bind each lifecycle result to its exact immutable request. An exact replay returns original evidence before new-action state checks. Unique request/message identities and one received terminal result per NewRx attempt or lifecycle request prevent duplicate effects. Unknown results must resolve the existing request before a new request of that action; later unavailability cannot downgrade unknown to failed, and a superseded request rejects a new result; no blind new request or resend is introduced.

Cancellation: received simulation acknowledgment appends a source-labeled `cancelled` event linked to the original attempt event, plus response evidence linked to that resolution. Rejection keeps the original unresolved; unknown stays reconciliation-required, and unavailable retains no received evidence. Pending cancellation blocks manual reconciliation bypass and replacement submission. Renewed exact-version review is required after cancellation/confirmed-not-sent reconciliation; unused earlier preparations become stale. The clinical order itself is never rewritten by a simulated cancellation.

Fill: the action is explicitly a **fill-notice simulation request**, not a pharmacy fill order. The received RxFill notice has no inferred drug, quantity, substitution, handed-over time, pickup, delivery, administration, financial completion or dispense record. Unknown/unavailable stay distinct from received notice. This optional notice workflow does not complete the prescription or unrelated care/tasks.

The API event/history read includes scoped request/response evidence. The Material UI fulfillment panel shows pending/result/source/correlations and separate save-request/result actions, preserving exact pending request bodies for explicit retry. Read-only users can inspect evidence but write actions remain permission-controlled in Rails. The paged worklist keeps original outcome and adds clearly labeled received simulation metadata and cancellation state/next action. Existing exact legacy NewRx receipt retrieval remains before new preparation validation.

## Conservative boundaries and partial/external limits

- This is source implementation only. No received event represents a real provider/pharmacy response or external acceptance, cancellation or fill.
- Live provider identity, message/schema mapping, callbacks, signature verification, response retention/redaction rules and sent/remote-received timing remain unselected and disconnected. No credentials, vendor endpoint, live call, automatic send or access provisioning was introduced.
- Historical rows are untouched. Attempts lacking original correlation/source provenance retain the existing documented manual reconciliation path; response/request identity is not inferred or backfilled. Existing correlated unknown attempts may receive an explicitly chosen new local simulated response at its new recording time, never a retroactive claimed receipt.
- New out-of-order results for already reconciled/replaced attempts are rejected without state change. Exact saved result replay remains possible. A pending fill-notice request overtaken by cancellation remains visible as historical pending work; it is not automatically completed or assigned an invented result. A future selected provider must define inbound quarantine/conflict reconciliation rather than reuse simulator behavior as partner acceptance.
- Existing manual reconciliation of recorded simulator evidence is retained when no cancellation request is pending; it does not invent received metadata. Controlled-mode local outcomes remain the preceding source's synthetic behavior, not EPCS or professional acceptance.
- No cancellation/fill request triggers clinical order edits, dispense/administration, stock, money, patient delivery or task completion. Refill approval remains on the existing separate workflow.
