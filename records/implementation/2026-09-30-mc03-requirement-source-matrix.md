## Explicit correction — searchable preferred language

After the scorer challenged the original matrix classification on 2026-09-30, Patch rechecked the preserved original registration table, current consolidated plan, decisions and repository source. The original says “Searchable language; Yes/No/Unknown.” No superseding decision removing searchability was found. The earlier row calling that control a suggestion/undefined was incorrect; this correction supersedes that classification. Searchability is an accepted requirement and **missing source**, while capture/persistence and interpreter tri-state are present.

At application candidate fd3e7c322e549cf84b589b54b77fd4cd21661e21, Patients.tsx uses the ordinary Field for primary_language, not a searchable selection control. Registration accepts any bounded entered string (maximum 80) and uses an explicit not-recorded value for blank input. Searches for language options/choices/catalog, ISO-639 and BCP-47 found no existing allowed-choice dataset or service. English/Spanish occur in development population samples; they are example values, not a selected vocabulary. PatientEducationPanel's English fallback is likewise not a choice catalog or authority to restrict registration language.

No product increment was implemented: the requested safe condition—reuse existing allowed choices while preserving manual input—has no discovered choice-set owner to reuse. Choosing a vocabulary, querying patient records for suggestions, adding a provider, or promoting fixture languages to policy would require a separate explicit contract. Once a choice set is identified or selected, a bounded free-solo searchable control can retain manual text, existing values, unknown/blank handling and the same API/persistence without changing clinical policy. Linked-activity duplicate reconciliation remains separately undefined and is not expanded by this finding.
