## Supported operation

This conservatively extends the [accepted single-draft text import](2026-09-30-mc15-bounded-offering-text-import.md), after inspecting the [original mapping review](2026-09-30-mc15-cross-clinic-mapping-review.md), `configurationMapping.ts`, and the existing `ManageServiceOffering`/controller/transport owners. It is an assisted sequence of already authorized updates, not a new migration privilege or catalog conversion policy. No new healthcare field, clinical default, terminology equivalence, or exchange contract is introduced.

The operator loads a different clinic's format-1 snapshot (existing 1 MB file limit and 500-record-per-group validation), explicitly checks each existing destination draft, chooses its source offering, and checks its text fields individually. No matching name or ID selects anything. Each source and destination may be selected at most once per review. No source locations, visit types, clinician eligibility, price references, operational settings, or profiles are mapped or applied.

The exact existing allowlist and constraints are reused: `name` (160 characters), `code` (50), `contact_instructions` (500), and `referral_instructions` (500). Null, absent, blank, oversized, unsupported, duplicate-field and no-op selections are rejected rather than clearing destination text. Destination code collisions and collisions between reviewed items are blocked; code swaps are not inferred. Selected destinations must belong to one loaded clinic and remain existing DRAFT offerings in the preview. Each optimistic revision protects against a concurrent publish/edit through the normal endpoint.

**Preview selected draft changes** freezes a before/after table for every changed field, source/destination IDs, expected revision, supplied source provenance, and one distinct request key per item. It sends no mutation. **Apply reviewed draft text** sequentially sends only those text changes, that item's `lock_version`, and its original `request_key` to its existing destination `PATCH /api/clinic/service_offerings/:id`. Ordinary offering create/edit/publish/retire controls and handlers are blocked while the bulk review is open. Existing server tenancy, current actor authorization, audit, optimistic revision, uniqueness and actor/practice-scoped idempotency receipts remain authoritative.

## Partial application and uncertainty

- Each item retains its exact request and independent ready/sending/applied/rejected/unknown state in browser memory. Successful items are never resent by **Apply unattempted reviewed items**.
- Application stops on the first rejection or uncertainty. Continuing unattempted reviewed items is another deliberate action. An unknown item blocks continuation and closing the review.
- Only **Retry exact change for #ID** resends an unknown item's original path/body/key/revision. A subsequent 401/403/409/422 denial cannot relabel its earlier unknown outcome as rejection or clear its request. Network errors, timeout, server failure, an explicit unknown outcome, session-change ambiguity, and malformed/wrong-destination success acknowledgments remain unknown.
- Success requires the existing endpoint's response identifying the destination offering/practice and its boolean `replayed` acknowledgment. Totals retain applied, unknown, rejected, unattempted and awaiting-confirmation counts. The all-applied message requires every reviewed item to be confirmed applied; rejected, unknown or unattempted items keep the review incomplete.
- Before any request, **Change selections** permits a fresh preview. After known rejection, the operator may close/reload/review a new change. Closing reloads offerings. Applied updates are not undone, and unknown outcomes are not hidden behind a close action.
