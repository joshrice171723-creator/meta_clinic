# Database change workflow

## When to use

Use for Rails migrations, `db/structure.sql`, data transitions, seed changes, permissions, restore logic or commands that can modify database state.

## Required preflight

1. Read `apps/api/AGENTS.md`, the relevant architecture/model notes, CICD and the exact transition/runbook.
2. Identify every target database by explicit name, environment and data classification. Confirm which are disposable scratch targets and which must be preserved.
3. Record outcome/boundary, failure trigger and harm, detection/guard, negative test, recovery/stop condition and exit evidence.
4. Define compatibility for existing rows, encryption identity, audit/history, retries and concurrent writers.

## Implementation

- Prefer a forward migration and additive/backfillable stages. Do not rewrite shared applied migrations.
- Keep data transformations bounded, deterministic and restartable. Validate row ownership and reconciliation before cleanup.
- Generate and inspect `db/structure.sql`; preserve database constraints and runtime grants.
- Use uniquely named scratch databases for verification. Cleanup names must be explicit and generated by the same harness.
- Never run broad `db:drop`, `db:reset`, wildcard SQL or an unresolved-variable cleanup against development, staging or production.

## Verification

Run the relevant Rails suite plus `bin/verify-backend` and `bin/verify-postgres` for schema, transition, concurrency, authorization or history changes. Test fresh setup, upgrade, rollback/failure handling, repeated execution and restore/reconciliation as applicable.

Hosted cutovers additionally require [`release.md`](release.md), explicit target authorization and preserved recovery evidence.
