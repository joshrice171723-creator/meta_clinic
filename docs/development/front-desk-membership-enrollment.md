# Front-desk membership enrollment

## Purpose and boundary

This is the staff-led counterpart to the public membership path. It lets an authorized front-desk member select a **published** clinic membership, record a prospective patient's contact details and move that enrollment into a dedicated telephone-style payment step.

It does not create a patient, confirm a payment, store or collect card details, determine eligibility, prescribe medication, schedule a clinical visit or establish a clinical relationship. This document records a product workflow and synthetic-development verification target; it is not clinical, legal, privacy, payment-provider or release approval.

## Flow

1. A staff member with `subscriptions.review` opens **Enroll membership** from Front desk.
2. The server provides the current practice's published membership versions. The staff member selects one, including any required service choices.
3. Staff records the prospective patient's name, email address (required for a receipt and future portal setup), optional phone number and explicit permission for clinic follow-up. The server creates an immutable `membership_prospect` with source `front_desk_enrollment`, intent `purchase` and relationship stage `prospective_patient`.
4. The enrollment remains in the front-desk dialog and presents **Take payment by phone**. It uses the existing Stripe Mail Order/Telephone Order (MOTO) reader flow; the enrollment does not enter the Growth call workflow. Staff records the patient's telephone authorization immediately before starting payment.
5. The existing staff phone-payment operation uses the configured Stripe reader path. Meta Clinic never receives raw card details. A failed, canceled, unknown or unconfirmed payment leaves the record out of patient onboarding and recoverable in the pipeline.
6. Only the existing server-verified payment completion can create the patient, activate membership onboarding, create the receipt/invitation and create the front-desk onboarding task. The browser return or a staff click is not proof of payment.

## Membership and clinical-review rules

- Published terms are immutable on the prospective-patient record, including price, renewal, cancellation and selected services.
- A membership flagged `eligibility_review` may be recorded for follow-up but is blocked from phone payment. Staff must not promise eligibility, a GLP-1 prescription, or a clinical outcome. The clinic must complete its separate review before any future payment path is enabled.
- No Good Faith Estimate is generated by this membership selection. Any required estimate workflow is distinct and must be assessed under the applicable cash-pay policy.

## Failure and recovery behavior

| Situation | Safe result | Recovery |
| --- | --- | --- |
| No published membership | No enrollment can be submitted | Publish a membership through the catalog workflow. |
| Duplicate submit/retry | The request key returns the same prospective-patient record | Continue with that record; do not create a second enrollment. |
| Same key, different data | Server rejects the conflict | Start a deliberate new enrollment after confirming the details. |
| Missing contact permission or email | Server rejects the request | Obtain/correct the required information before saving. |
| Review-required membership | Enrollment is retained; payment is blocked | Use the clinic's separate review workflow. |
| Payment failure, cancellation or unknown state | No patient/onboarding is created | Use the existing pipeline’s follow-up and status-reconciliation controls. |

## Standards and requirement mapping

No selected U.S. FHIR implementation guide governs commercial membership sign-up or staff payment intake. The workflow therefore uses the existing tenant-scoped membership/prospect model and begins FHIR Patient mapping only after the verified-payment path creates an actual patient. No exchange partner is selected by this change.

| Source/decision | Requirement | Backend/UI mapping | Verification target |
| --- | --- | --- | --- |
| D-069 / D-070 | Only verified payment creates a patient and onboarding | `StaffEnrollment` creates only a prospect; the established verified-payment service owns conversion | Focused integration test proves zero patients before payment. |
| D-069 | Review-required offers remain contact-first | `StaffPhonePayment` rejects `eligibility_review`; UI explains the gate | Focused service test proves payment cannot start. |
| EN-03, EN-04, EN-05, EN-06, EN-07; OP-01, OP-02, OP-04 | Preserve terms, identity uncertainty and payment recovery | Immutable terms/request digest, duplicate detection and existing payment pipeline | Targeted request/idempotency and regression tests. |

## Acceptance walkthrough

1. Sign in as an authorized synthetic front-desk member and open Front desk.
2. Select **Enroll membership**, choose a published GLP-1 or diet-management membership, enter synthetic contact details and save.
3. Confirm the result is a prospective patient, not a patient, then use **Take payment by phone** in the same dialog.
4. Confirm telephone-payment authorization and enter the card details on the assigned MOTO reader. Check payment status before retrying, and confirm activation only after the server reports verified payment.
5. Repeat with a review-required membership and confirm the record saves but payment is blocked.
