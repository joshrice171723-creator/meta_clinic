# Multi Clinic Demo Sandbox

## Assignment and authority

- **Assignment:** Expand the sandbox into a convincing, resettable, organization-wide fictional clinic environment covering two clinics, two locations per clinic, 10–20 staff per location, about 300 patients per location, and about 60 visits per location per week.
- **Scale arithmetic:** Four locations; 40–80 staff; approximately 1,200 patients; approximately 240 visits per week, or about 1,920 visits over eight weeks. “About two months” means a coherent eight-week operating history plus a forward billing/scheduling horizon; choose and document the exact seed window during implementation so dates remain deterministic and visible.
- **Authority:** Planning only. The user asked to create a plan, not implement, deploy, publish, or contact vendors. Use independently invented synthetic data; no real or real-derived people, clinics, claims, payment credentials, vendor requests, or outbound messages.
- **Approved outcome:** A sandbox that feels operationally populated and permits exploration of historical and upcoming billing, membership activity, staffing, scheduling, patient panels, and site-specific inventory.
- **Existing product model:** The organization → clinics (practices) → locations (sites) hierarchy already exists, as do organization/clinic/location selection and organization summaries. The gap is realistic, coordinated seed data across this existing hierarchy; the current guided-demo creator starts one practice at a time.
- **Exclusions:** No live Stripe/payment or supplier traffic; no clinical claims/readiness implication; no unsandboxed source-record mutation; no fabricated clinical encounters/results; no production data or migration.
- **Continuity instruction:** A building agent reads this brief and its linked canonical references before starting, resuming after context reset, or accepting handoff; compares this baseline against current code and newer user direction; resolves drift before dependent edits; checkpoints completed slices, blockers, material changes, and handoffs. This brief is guidance, not implementation authority or proof.

## Fields and action rules

- **Organization and clinic structure:** create/use one existing `Organization`, two existing clinic/practice records under it, and two existing `Site` locations per clinic. Preserve practice-scoped domain data and existing cross-practice access rules; organization grouping does not grant cross-clinic access by itself.
- **Site:** existing site identity, code, status, address, operating hours, rooms, timezone and clinic association; generated values must be internally consistent and clearly fictional.
- **Staff:** existing workforce/staff member, employment and site assignment records; 10–20 active people per site. Avoid creating fake user logins unless a demonstrated workflow requires the account and its existing authorization grants.
- **Patients:** 300 per intended site cohort as a target; use generated names/references and minimal demographic fields permitted by existing models. Current patient rows are clinic-scoped without a site foreign key. During implementation choose an existing supported relationship or add a narrowly owned location association if the location panel must be filterable. Do not infer a patient's home location from one visit or claim a location-specific count from the practice-wide patient query.
- **Visits:** target ~60/week/site over eight historical weeks and a small future schedule. Use supported appointment states and ordinary booking services; scheduled visits are not encounters, clinical evidence, completed billing or proof of service.
- **Billing history:** realistic but simple USD examples with stable dates and amounts. Invoice schema states are `draft`, `posted` and `void`; paid/open are derived from payments, allocations and credits, not invoice status values. Link invoices to patients and supported charge concepts without inventing insurance claims. Align persisted creation/payment timestamps with the visible history: the current Income outlook groups by `created_at` and averages three historical months, so two months of transactions need a deliberate forecast treatment.
- **Memberships:** use published synthetic subscription terms and local simulator outcomes. Mix active, canceled-at-period-end, ended and failed-renewal cases only where supported. Do not equate a future renewal projection with a posted invoice or collected payment.
- **Inventory:** existing product/SKU/unit/package, supplier, site-bound storage location, lot/expiry, receipt, adjustment and purchase order records; create values through existing services so exact quantities and immutable history remain valid.
- **Reset contract:** one named demo organization/run ID owns all fixtures across two practice IDs. Current `development_demo_runs` has only `practice_id`, and `SharedDemoLesson` resets only that practice. Extend ownership/session binding and targeted teardown for both clinics before writing a second clinic's data. Never use broad tenant wipes or reset a shared development database. Reset must reject unknown/ordinary tenants and must not weaken demo route, session, release, or role guards.

## Implementation and acceptance

1. **Architecture/data inventory:** use the route table and current schema to map the existing organization, practice, site, staff employment, patient, appointment, invoice/payment, subscription, inventory and demo-run models/operations. Confirm organization → two practices → two sites per practice. Record for each priority route its source query, practice/site scope, pagination and permission. No new organization hierarchy is needed.
2. **Seed-story design:** define a compact set of recognizable storylines (new member, steady member, failed renewal needing review, upcoming renewal, paid historical invoice, open balance if supported, low-stock lot, upcoming appointments) while filling the population to requested scale. Keep names and event dates reproducible.
3. **Generator:** add a demo-specific orchestration layer that calls existing creation/workflow services in dependency order, is idempotent, uses bounded batches, and records ownership/run identity. Prefer deterministic pseudorandom fixtures with a fixed seed. Avoid callbacks that send reminders or external effects.
4. **Timeline:** generate approximately eight weeks of appointment and billing history ending at the selected demo “today,” plus forward bookings and renewal projections. Ensure weekly visit counts average about 60 per site and fit hours, rooms, clinician capacity and workforce shifts (roughly 12 visits per weekday if open five days). Historical invoice/payment creation dates must drive the real billing charts. The Income outlook currently divides three historical months by three, so select a truthful projection rule for a two-month-old clinic and show how much history underlies it. Do not backdate events through APIs that enforce chronology unless the domain provides a supported simulation clock/fixture path.
5. **Populate domains:** sites/rooms/hours/offers; staff, employment and shifts; patient cohorts; appointments and selected linked work; subscription catalog and memberships; persisted invoices/payment simulator events; inventory products, suppliers, orders, lots, locations, receipts, movements and reorder states. Preserve cross-domain references and state semantics.
6. **Entry/reset UX:** expose recognizable organization and location context, a clear “as of” date, and a safe reset/reseed operation. Keep demo projection labels distinguishable from persisted financial obligations without adding repetitive global banners.
7. **Focused verification (only when implementation is authorized):** verify organization/site counts, site staff assignments, the defined patient cohort rule, weekly appointment distribution, invoice/subscription temporal coherence and Income outlook values, simulator-only payment provenance, inventory quantity reconciliation, reset/retry idempotency, demo isolation, and that no outbox/provider job can dispatch. Walk through the priority routes in the table with organization, clinic and location switching, including pagination and filtered views. Do not add or run tests without explicit user request under repository policy.

**Acceptance:** the four locations each show 10–20 assigned staff and approximately 300 patients under a documented, supportable location cohort rule; each location averages about 60 visits/week through the eight-week history and has visible upcoming appointments; the current billing dashboard and Income outlook show coherent persisted history and labeled estimates; inventory routes show location-specific quantities and a traceable order-to-stock story; priority work queues show linked, actionable examples; reload preserves the baseline; reset recreates the same synthetic story across both clinics; every record is demo-owned and isolated; no external payment, supplier, communication, or clinical claim is emitted.

**Dependencies/stop conditions:** ensure a demo run can own and reset both practices and all four sites as one isolated organization without broad deletion or cross-practice data leakage. The current run is single-practice, so plan a safe demo-run-to-organization association or an existing supported grouping before implementation; do not duplicate the Organization model. If supported billing lifecycle cannot safely represent a proposed state, omit that state rather than fabricate it. No medical notes/results, payment credentials, real supplier catalog, or live transactions.
