# Multi Clinic Demo Sandbox

## Assignment and authority

- **Assignment:** Expand the sandbox into a convincing, resettable, organization-wide fictional clinic environment covering two clinics, two locations per clinic, 10–20 staff per location, about 300 patients per location, and about 60 visits per location per week.
- **Scale arithmetic:** Four locations; 40–80 staff; approximately 1,200 patients; approximately 240 visits per week, or about 1,920 visits over eight weeks. “About two months” means a coherent eight-week operating history plus a forward billing/scheduling horizon; choose and document the exact seed window during implementation so dates remain deterministic and visible.
- **Authority:** Implementation requested on 2026-09-25. Use independently invented synthetic data; no real or real-derived people, clinics, claims, payment credentials, vendor requests, or outbound messages.
- **Approved outcome:** A sandbox that feels like a full operating clinic: historical and upcoming billing, memberships, staffing, scheduling, longitudinal patient journeys of different types, clinical work, prescriptions, laboratory follow-up, site-specific inventory, and the small connection states that tie those workflows together.
- **Existing product model:** The organization → clinics (practices) → locations (sites) hierarchy already exists, as do organization/clinic/location selection and organization summaries. The gap is realistic, coordinated seed data across this existing hierarchy; the current guided-demo creator starts one practice at a time.
- **Exclusions:** No live payment, supplier, pharmacy, lab, video or messaging traffic; no clinical-readiness implication; no mutation outside demo-owned synthetic organizations; no real patient data migration. Fictional encounters, notes, orders and results are in scope where their provenance and workflow states are coherent.
- **Continuity instruction:** A building agent reads this brief and its linked canonical references before starting, resuming after context reset, or accepting handoff; compares this baseline against current code and newer user direction; resolves drift before dependent edits; checkpoints completed slices, blockers, material changes, and handoffs. This brief is guidance, not implementation authority or proof.

### Patient Flow coverage across different types

The shared Patient Flow owns patient selection and connected scheduling/care handoff. Use the two configured clinics for distinct supported service mixes, then cover these journey variations with coherent patient, appointment, encounter, task and financial references. Record the exact clinic configuration and visit type for every case. If a specialty requires an incompatible `clinic_type` or unselected service scope, use a separate clearly labeled scenario/profile instead of forcing it into one of the two clinics.

| Journey variation | Seeded connected path and visible result |
| --- | --- |
| New membership patient | Public interest/prospect → account setup → local simulated payment outcome → patient/active agreement → intake → first booking → visit → invoice/renewal. Include abandoned and failed checkout as prospects, never patients solely because a form was opened. |
| Established patient, routine follow-up | Prior chart/visit → returning intake or confirmation → scheduled/arrived visit → updated note/plan → checkout and next visit. Preserve earlier revisions and show current versus historical information. |
| Walk-in and same-day concern | Identity search/register or locate existing patient → same-day appointment/walk-in → front desk check-in → team handoff → encounter → checkout or owned follow-up; include a canceled/no-show branch separately. |
| Urgent or specialty outpatient visit | When a clinic's selected type/service scope and visit catalog allow it, show distinct reason, timing, clinician/room assignment, intake and follow-up routing. Do not add an urgent-care or specialty label alone and claim that its workflow was exercised. |
| Video visit | Video-eligible booking and preparation/consent → local visit/encounter work → wrap-up and follow-up. Show configured/disconnected provider state truthfully; no fake two-party media session. |
| Weight management | Configured initial and follow-up forms, measurements with source/time, goals, plan revision, medication or laboratory work where selected, renewal and longitudinal progress. No automatic dose or treatment recommendation. |
| Behavioral health / medication management | Only in a clinic/profile configured for behavioral health: initial/follow-up, appropriate intake/assessment source, clinician review, versioned medication request, refill or therapy/referral coordination and owned open work. Private psychotherapy-note examples require their existing originator-only access path; no disclosure through general views. |
| Procedure, in-office medication and vaccination | Only if the exact service scope and inventory rules are enabled: order/review → appointment → actual administration or take-home handover → linked lot movement and documentation → follow-up. A prescription for an outside pharmacy does not consume clinic stock. |
| Laboratory and result follow-up | Service request and specimen/collection state where supported → manually sourced synthetic result → review, correction/recollect or patient contact task → independent scheduling while a result is pending. |
| Prescription and refill | Encounter medication request draft → exact-version review → outside-pharmacy simulated attempt with accepted/rejected/unknown examples, or separate in-house dispense/administration with stock link. A refill request stays a request until reviewed and a new authorized order is recorded. |
| Financial and access branches | Cash-pay, included membership visit, unpaid/partial invoice, cancellation/refund, and optional saved coverage/claim preparation only where enabled. Keep payment collection, eligibility and external acceptance distinct. |
| Role handoff and recovery | Front desk, nurse/clinical staff, clinician, billing, inventory and administrator personas see the same linked patient/visit through their own permitted screens. Include pending ownership, accepted transfer, blocked dependent action and independent work that remains available. |

Use ordinary background volume for the approximately 1,920 visits and a smaller set of linked, inspectable example patients for every variation. Set a documented distribution of visit types, arrivals, completions, cancellations, no-shows, open notes/tasks and future bookings. A completed encounter needs the supported completion/documentation state; do not relabel a scheduled appointment as a completed visit to reach the count.

## Fields and action rules

- **Organization and clinic structure:** create/use one existing `Organization`, two existing clinic/practice records under it, and two existing `Site` locations per clinic. Preserve practice-scoped domain data and existing cross-practice access rules; organization grouping does not grant cross-clinic access by itself.
- **Site:** existing site identity, code, status, address, operating hours, rooms, timezone and clinic association; generated values must be internally consistent and clearly fictional.
- **Staff:** existing workforce/staff member, employment and site assignment records; 10–20 active people per site. Avoid creating fake user logins unless a demonstrated workflow requires the account and its existing authorization grants.
- **Demo roles:** create only the synthetic logins/memberships needed to demonstrate front desk, clinical staff, clinician, billing, inventory and administrator handoffs. Apply existing role grants and site access; counts of staff directory entries do not imply working logins. Switching roles must preserve a shared underlying record and enforce the server's permissions.
- **Patients:** 300 per intended site cohort as a target; use generated names/references and minimal demographic fields permitted by existing models. Current patient rows are clinic-scoped without a site foreign key. During implementation choose an existing supported relationship or add a narrowly owned location association if the location panel must be filterable. Do not infer a patient's home location from one visit or claim a location-specific count from the practice-wide patient query.
- **Visits:** target ~60/week/site over eight historical weeks and a small future schedule. Use supported appointment states and ordinary booking services; scheduled visits are not encounters, clinical evidence, completed billing or proof of service.
- **Billing history:** realistic but simple USD examples with stable dates and amounts. Invoice schema states are `draft`, `posted` and `void`; paid/open are derived from payments, allocations and credits, not invoice status values. Link invoices to patients and supported charge concepts without inventing insurance claims. Align persisted creation/payment timestamps with the visible history: the current Income outlook groups by `created_at` and averages three historical months, so two months of transactions need a deliberate forecast treatment.
- **Memberships:** use published synthetic subscription terms and local simulator outcomes. Mix active, canceled-at-period-end, ended and failed-renewal cases only where supported. Do not equate a future renewal projection with a posted invoice or collected payment.
- **Clinical history:** versioned intake, encounter, note, assessment, plan, result, medication request and follow-up records for selected synthetic personas. Use configured specialty forms and explicit provenance; bulk background encounters use a bounded, reviewable fixture recipe rather than invented treatment decisions.
- **Prescriptions and fulfillment:** distinguish draft/authorized medication requests, prescription events and simulated transmission attempts, refill requests, outside-pharmacy destinations, local dispense/administration, and inventory movement. Review and destination must refer to the exact order version. Rejection/unknown cannot silently become accepted; in-house stock is consumed only by an actual supported fulfillment operation.
- **Inventory:** existing product/SKU/unit/package, supplier, site-bound storage location, lot/expiry, receipt, adjustment and purchase order records; create values through existing services so exact quantities and immutable history remain valid. Include ordinary clinical/office supplies and selected medication products, variable demand across sites, reorder pressure and traceable replenishment.
- **Connectors:** configure only locally supported simulated/manual states and source-labelled outcomes. Keep outboxes suppressed and provider credentials absent in seeded data; preserve pending/rejected/unknown states and a staff recovery path without generating external work.
- **Reset contract:** each visitor's sandbox lesson owns a primary practice and a hidden companion lesson owns the second practice in the same demo organization. Re-entry resets only those two registered practice IDs in one transaction, then recreates their fixtures around the current business date. Other visitors' runs, records and sessions must stay active. Never use broad tenant wipes or reset an ordinary development database. Reset must reject unknown/ordinary tenants and preserve demo route, session, release and role guards.
